### Which official challenge this answers

The official site pairs the Boston 311 dataset with these two challenges (paraphrased):

- **More Responsive Neighborhood Services.** High report volume and repeat reports make
  patterns hard to see and progress hard to communicate. Suggested angles: issue triage,
  **geographic patterns**, **service transparency**, and more accessible resident feedback.
- **V2 · Responsive and resilient communities.** The context line says that *volume hides who
  is waiting.*

311 Wait maps onto this directly. The survival analysis provides the **service
transparency** (a median over closed cases leaves out the people still waiting). The God's-eye map
shows the **geographic pattern** (where those open cases are right now).

## 1. What the service does

A median closure time taken over closed cases only leaves out the thousands of 311 requests
still open, which tend to be the slow ones. (This is not a claim about how the city computes
anything; see `docs/research/claim-check.md`.) **311 Wait puts them back in.** It applies **Kaplan–Meier**
to time-to-closure, counting still-open cases as censored, and **Aalen–Johansen**
competing-risks incidence to separate requests closed as *resolved* from those closed as
`Noted` (no action required) or `Transitioned` (reassigned to another agency). It then maps where the open and overdue cases are
today. It makes **no causal claim**: it audits the measurement and shows `n`, censoring counts,
and confidence intervals. The estimators are implemented three times independently (Kiro
TypeScript, a Python reference, `lifelines`) and agree to six decimal places.

Audiences: a **resident** who wants a plain answer, and a **judge or journalist** who wants
the audit.

## 2. Data source — the hackathon's 311 API

We use the dataset the hackathon designates: **Boston 311 service requests**, CKAN resource
`254adca6-64ab-4c5c-9fc0-a6da622be185` on `data.boston.gov`. `src/lib/boston311.ts` already
targets this exact resource.

- **Same API, different action.** The hackathon's example link uses CKAN `datastore_search`,
  which returns rows in pages of 100. We use `datastore_search_sql` on the same resource and
  host, so totals and per-service survival inputs come back in one round trip instead of
  hundreds of pages. No key either way. *If the organisers require the `datastore_search`
  action specifically, we switch the build-time fetch to it; the statistics don't change.*
- **Fields.** The hackathon's sample selects `open_date, case_topic, service_name,
  assigned_department, case_status, neighborhood, zip_code, on_time, city_council_district,
  ward`. We also need `close_date` and `closure_reason` (survival), and `latitude`/`longitude`
  (map). All of these are in the same resource.
- **Cohort.** Every query keeps `open_date >= 2026-07-01` (rationale in the spec's design.md).
- **Definition of "open" (decision needed, §9).** `case_status` has four values in the cohort:
  `Closed` 48,903 · `In progress` 7,876 · `Needs Reallocation` 16 · `Create` 2. The docs quote
  7,876 (In progress only); every non-closed status gives 7,894. Pick one and use it in every
  figure.
- **Avoid Boston's Open311 API** (`311.boston.gov/open311`). Its anonymous limit is 10
  requests per minute, which public traffic would exceed.

Live check (2026-10-24): all 7,894 non-closed cases have coordinates; the most repeated point
has only 6 cases, so the city is not substituting a default location; 25 named neighbourhoods
plus 37 cases with no neighbourhood.

## 3. Website structure

One scrolling public audit document — **not a dashboard** — in progressive-disclosure layers.

```
App
├─ Header          title · one-line thesis · data timestamp
├─ AnswerLayer     ServicePicker (from live data) · HeadlineGap (data vs city)
├─ CityMap         God's-eye map (§3.4)
├─ EvidenceLayer   SurvivalChart · BiasCallout · CompetingRisksBar · NeighborhoodTable
└─ MethodLayer     cohort · assumptions · confounders · links · attribution
```

### 3.1 Layer 1 — the answer (above the fold)
Service picker driven by the data, not a hardcoded list (this answers the cherry-picking
objection). One very large headline number beside a smaller comparison: **what the data shows**
vs **what the city reports**. Plain words only — no "median", "censored", "estimator".

### 3.2 Layer 2 — the evidence
- **Survival curves:** Kaplan–Meier vs the naive closed-only estimate, with a Greenwood 95%
  band. Recharts `type="stepAfter"` + `<Area>`; never a smooth curve.
- **Bias callout** (REQ-06): the exact naive-vs-corrected sentence, full width.
- **Competing-risks bar:** resolved / closed-not-fixed / still open, each segment labelled with
  its percentage.
- **Neighborhood table:** on-time rate with Wilson intervals, sortable; cells under n=30 show an
  em dash and a focusable explanation.

### 3.3 Layer 3 — the method
Cohort window and why it starts 2026-07-01, the independent-censoring assumption and which way
it biases, named confounders, data timestamp, link to `ANALYSIS.md`, map attribution.

### 3.4 The God's-eye map

Shows what is **open and overdue right now**, at three zoom levels:

1. **City — choropleth.** Neighbourhoods shaded by the count of open cases already past the
   city's own target.
2. **Neighbourhood.** Selecting one filters the Layer 2 charts to that area.
3. **Street — clustered points.** Open cases grouped into numbered clusters that split as you
   zoom, coloured by how far past target. Selecting a point shows service type, age, status.

**Rendering stack**
- **MapLibre GL JS** (BSD-3) renders the map.
- **Protomaps PMTiles** base map: a single Boston-only `.pmtiles` file, served as a static
  asset from the same Vercel deployment. MapLibre reads only the tiles it needs from it. No tile
  server, no API key, no third-party provider, and nothing that breaks under public traffic
  (OpenStreetMap's own tile servers have limited, donation-funded capacity and a usage policy).
  The file is cut from a Protomaps build with `pmtiles extract` and a Boston bounding box by a
  committed script, so the map is reproducible from a clean clone.
- **Point clustering** with MapLibre's built-in GeoJSON clustering (Supercluster, ISC), so no
  extra dependency.
- **Neighbourhood polygons:** Boston Neighborhood Boundaries (city open data), simplified at
  build time to about 150 KB with mapshaper. Joined on `name` ↔ 311 `neighborhood`; the join is
  checked for all 25 names at build time, and the 37 cases with no neighbourhood are reported as
  a count rather than dropped silently.
- **No `react-leaflet`** (Hippocratic-2.1, not OSI-approved).

**Map honesty and privacy**
- Labelled a **snapshot of open cases, not a rate** — cases of different ages, not a score.
- **Privacy:** the hackathon describes this dataset as having no street address, and these
  are reports made by residents. Street level therefore shows clusters, and individual points
  use coordinates rounded to about 100 m (3 decimal places), never the exact reported spot.
- Colour is never the only channel; every shaded area exposes its number. All map findings also
  appear in the neighbourhood table, so the map is never the only way to reach them.
- Required credit, visible in the map corner: `Protomaps © OpenStreetMap`.

## 5. Design and accessibility

- A civic **document**: light background, typography-led, tabular figures; the largest thing on
  the page is a number.
- Three colour roles only: accent (what the data shows), muted (what the city reports), alert
  (overdue).
- Keyboard-operable everywhere with visible focus; WCAG AA contrast, checked; charts and map are
  never the only carrier of a finding; `aria-live` on figures when the service changes.
- Copy rules: "closed" ≠ "resolved"; every figure shows `n` and the censored count; no causal
  language; no income-gradient framing (tested and disproven).
- Claude skills (via Conductor), read before the matching code: `dataviz` before any chart,
  `web-design-guidelines`, `ecc:frontend-a11y`, `ecc:make-interfaces-feel-better`. Not
  `taste-skill:design-taste-frontend`.

## 6. Data pipeline (no backend)

```
build time:  scripts/fetch_cohort_cases.sh  → public/data/snapshot.json
             scripts/build_basemap.sh       → public/map/boston.pmtiles
             scripts/build_boundaries.sh    → public/map/neighborhoods.json (~150 KB)
runtime:     static files → src/lib/stats.ts + boston311.ts → components
```

`src/lib/**` is finished and frozen. If a statistic is missing, it is added to the spec and
built in Kiro, never recomputed inside a component.

## 7. GitHub and Kiro automation

**GitHub Actions** (`.github/workflows/`)
- `ci.yml` — on every pull request: `npm ci`, `npm test`, `npm run build`, and the `lifelines`
  cross-check. The triple-verified statistics are re-verified on every change.
- `refresh-data.yml` — on a schedule: re-run the fetch script, commit the new snapshot, and let
  Vercel redeploy. Numbers stay current without a backend, and git keeps a dated history of
  snapshots.

**Kiro** (judged under Implementation; neither exists yet)
- `.kiro/hooks/` — e.g. run the statistics tests when `src/lib/**` changes, and run the
  accessibility check when a component is saved.
- `.kiro/settings/mcp.json` — MCP servers used during the build, documented in `KIRO-USAGE.md`.

## 8. Build order

Work happens on branch `wait-audit-ui`, with PRs into `main`. Each step is its own commit and
ends with a `KIRO-USAGE.md` entry, so the history stays reversible to the original scaffold.

1. **Scaffold cleanup** — replace the leftover "Manila / ClimaTech" `App.tsx`, rename the package
   to `wait-audit`, confirm `npm test` (17 passing), generate the data snapshot.
2. **CI workflow** + first Kiro hook.
3. **Layer 1** — ServicePicker, HeadlineGap.
4. **Layer 2** — SurvivalChart, BiasCallout, CompetingRisksBar, NeighborhoodTable.
5. **Layer 3** — method section.
6. **Map 1** — Protomaps base map + neighbourhood choropleth.
7. **Map 2** — neighbourhood selection filters Layer 2.
8. **Map 3** — clustered street-level points (rounded coordinates).
9. **Accessibility + polish pass** — axe-core and skills.
10. **Data refresh workflow.**
11. **Vercel deploy** — *only when explicitly requested.*

Floor to ship: the censoring correction and the competing-risks breakdown. The map is the
first enhancement; everything after it can be cut.
